# 项目经验

## 2026-08-10 - 视觉升级必须保留已确认的产品基线

- 在没有新的设计定稿时，不要用“提升可读性”为理由同时放大所有字号、卡片间距和装饰层级。
- DishLens 的菜单列表应保持安静、紧凑、便于快速扫读；新增图片状态、推荐和点单能力时，应沿用现有卡片结构，而不是重做视觉语言。
- 视觉修改必须提供前后截图并覆盖首页、菜单列表、详情页三条核心路径；功能改进与视觉重构应拆分提交，便于独立回退。
- 加载/识别状态不能只判断字段是否存在；数组结果必须验证 `length > 0`，终态必须分别处理成功、部分成功和全部失败。

## 2026-08-11 - 历史 UI 还原必须使用精确版本基线

- 用户指出“回到之前版本”时，先通过 Git 历史和关键页面特征定位唯一提交，再以该提交逐文件比对，不能根据记忆做近似还原。
- UI 与业务逻辑必须分层处理：恢复 JSX 视觉、文案和样式时，保留最新的识别状态机、缓存、图片兜底、分享渠道和错误处理。
- 一次视觉版本还原必须覆盖该版本的完整页面族，包括加载、首页、结果、详情、历史、收藏、点单和分享；只改三条主路径会留下混合视觉。
- 为历史视觉的关键识别特征增加回归测试，例如中央加载动画、细进度条和不存在阶段卡片，防止后续无意覆盖。

## 2026-08-11 - 生产关键链路必须消除可休眠和跨云依赖

- 正式数据库、任务状态和永久图片不能依赖会自动休眠的免费层服务；恢复后“暂时可用”不等于满足生产稳定性。
- Web/API、主数据库、任务缓存、队列和对象存储应放在同一云、同一区域，避免把每一次识别变成跨云网络调用；外部 AI 只作为可重试、可替换的异步增强。
- Redis、进程内存和本地文件都不能成为终态菜单结果的唯一来源；终态必须落入高可用 PostgreSQL，缓存丢失后可以完整重建。
- 数据库只保存稳定对象键和版本，不保存会过期的模型结果 URL 或供应商签名 URL；图片统一通过自有 CDN 域名读取。
- 汇报“正式库菜品数量”时必须实时查询正式数据库，并与本地知识库数量分开报告，不能把 317 条正式数据和 1022 条本地知识条目混为同一个指标。

## 2026-08-11 - 云模型欠费错误必须先定位到具体凭据

- DashScope 返回 `Arrearage` 只能证明当前请求使用的 API Key 所属账户或工作空间不可用，不能直接推断用户的整个阿里云账户欠费。
- 生产环境和本地环境对比时只输出密钥指纹与长度，不输出原文；先用文本请求，再用真实菜单视觉请求验证目标模型，均成功后才替换生产凭据。
- Next.js 生产进程可能从工作目录的 `.env.production` 读取变量，而不是从 `/proc/<pid>/environ` 读取；排查时必须同时检查 PM2 进程环境和应用工作目录环境文件。
- 模型供应商顺序要与当前可用主模型一致。本次 Qwen 恢复后使用 `MENU_AI_PROVIDER=qwen,gemini`，避免先等待已限流的 Gemini 再调用 Qwen。

## 2026-08-11 - 失败图片状态不能成为永久缓存终态

- 缓存结果里已有成功图片时，只补缺图，不重写成功 URL。
- `image_status=failed` 表示某次供应商或持久化尝试失败，不表示这道菜永久不可生成；后续缓存命中必须允许有界重试。
- 一批图片部分成功时终态会是 `partial`；重试资格不能只检查整体 `failed`，否则剩余失败项会永久留在缓存中。
- 状态机应先计算动作资格，再修改展示状态；不能先把 `failed` 改成 `processing`，随后又用新状态判断是否启动重试。
- 多层调用不得各自重新推导易变状态；将刷新资格封装为不可变计划并显式传入执行函数。
- 性能目标必须拆成客户端上传、服务端 intake、首页面模型和完整文本四段；跨洲上传耗时不能错误归因到 OCR 模型。
- 视觉模型选型要用同图、同提示词、隔离进程的真实菜单 A/B；本次 `qwen3-vl-flash` 四页 49 道首结果 9.25s，优于 `qwen3-vl-plus` 的 13.79s。
